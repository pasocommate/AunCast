# AunCast ユーザーマニュアル 執筆スタイルガイド

`Manual/`（MkDocs ユーザーマニュアル）を書くときの方針をまとめたものです。マニュアルを追加・編集する際は必ず従ってください。

> 本ファイルは `docs_dir: src` の外に置いてあるため、公開サイトには含まれません（保守者向けの内部ドキュメントです）。

---

## 1. 想定読者とトーン

- 読者は **社会人**（学生ではない）。VRChat ワールドを制作・運営できる程度に **Unity / VCC / プレハブ / インスペクタ / VR アプリ** を理解しているが、**C# やソフトウェア開発の知識はない**。
- **専門的で簡潔な文体**で書く。口語的・幼い表現は避ける（例：裏で・こっそり・そっと・みんな・パンク・ちゃんと・〜のコツ）。
- 一方で **開発者ジャルゴン（C# 等）は増やさない**。
- 言い換えの例：「配信サーバーがパンク」→「過負荷」、「直す／立て直す」→「復旧する」、「予備の側／いま流している側」→「予備系統／現用系統」。

## 2. 音声優先の前提（重要）

- **主役は音声（音楽）。映像はあくまで演出。**
- 想定ユースケース：ライブ会場となるインスタンスで、出演者が演奏する音楽を配信に載せてワールド内へ流す。観客は主に **出演者のアバターを注視** しており、配信映像は注視対象ではない。
- したがって最優先は **音声を途切れさせない・ズレさせない** こと。
- 記述順・強調は **音声を先**に（「音声・映像」の順）。症状の列挙なども音声を先頭にする。
- 「観客」は **同じインスタンスにいる VRChat ユーザー**を指す（配信を見ているだけの人ではない）。

## 3. 用語の統一

| 使う | 使わない |
|---|---|
| スタッフ | ワールド制作者 / イベント運営者 / 設置者 |
| 観客 | 視聴者 |
| 観客 / VRChat ユーザー | プレイヤー（ユーザーの意味） |
| 再生系統 / ビデオプレイヤー | プレイヤー（再生機構の意味） |
| ローカル | 自分の端末 |
| HUD ゲージ | 目の前にゲージ |
| VRChat ディスプレイネーム | （単なる）名前 |
| URL として不正なフォーマット | おかしな URL |
| 再生ステータス表示 | 状態の文字 |
| 過負荷 | パンク |
| 現用系統 / 予備系統 | いま流している側 / 予備の側 |

- **UI ラベル・インスペクタ表示名は実物どおり**に書く：Resync / Reboot / Stop All / Resync All / Connections / Concurrent / Drift / Audio Level / Silence Resync / Volume、および AunCastSettings の各表示名（同時接続上限・同時Resync上限 等）。
- **「スタッフ」の範囲**：ワールド制作担当とイベント運営担当（当日の配信操作を含む）をまとめて **スタッフ** と呼ぶ。作業範囲を区別したい場合は「初期設定を行うスタッフ」「配信を管理するスタッフ」のように補足する。
- **「プレイヤー」単独では書かない**：VRChat のユーザーを指す場合は **観客** または **VRChat ユーザー**、映像・音声の再生機構を指す場合は **再生系統** または **ビデオプレイヤー** と書く。`Player A/B` のような実オブジェクト名を書く場合も、必要に応じて「A/B再生系統」を添える。
- **Resync と Reboot の呼び分け**：本システム独自の 2 系統方式の再同期を **Resync**、全断→再接続を **Reboot** と呼ぶ（一般的なライブ配信再生システムが「Resync」と呼ぶ操作は、本システムの Reboot に相当する）。
- **再同期(Resync) の定義**：ドリフト（再生位置のズレ）を検出して再接続し、再生位置を **なるべく揃える** 処理。全員を厳密に一致させるものではない。この復旧を **自動化** するのが本システムの目的。

## 4. タイポグラフィ（日本語の書式）

- **和文ダッシュ「――」は使わない**（英文的で和文だと読みづらい）。代わりに（）や：などを用いる。
- **一桁のアラビア数字・一文字のアルファベットは全角**にし、**前後にスペースを入れない**（例：`2 系統`→`２系統`）。
- **2〜4 文字程度の英略語は半角可**だが、**和文との間にスペースを入れない**（例：`VR は`→`VRは`、`VCC の`→`VCCの`）。長い英単語・製品名（Resync, AunCast, Player A/B 等）は無理に詰めない。
- **半角のまま残す**：バージョン（2022.3）・小数（0.3）・多桁の範囲（10〜15）・負値（-60）・英語 UI ラベル（(L)/(R)）・`3D`・コード（バッククォート内）。
- **前提知識を要する図（UML のシーケンス図など）は使わない**。プレーンな箇条書き・表・文章で説明する。

## 5. 構成

- **前に要点、後に詳細**：先頭に「動作原理」と「クイックスタート」を置き、詳しい仕様は後続の各章に置く。
- **章の順序は スタッフ → 観客**。スタッフ向けの中では、導入・初期設定 → 配信運用の順に置く。
- 「はじめに」は簡潔に。**動作環境にはパッケージ名・バージョンを載せず**、Unity バージョンと依存の箇条書きのみとする。
- **`Docs/` 配下は開発者向けなので、マニュアルから案内しない**（GitHub Issue へのリンクは可）。

## 6. スクリーンショット

- 実 UI のスクリーンショットを使い、`Manual/src/assets/` に意味のある名前で配置する。

## 7. 校正マークアップ

- 校正指示は HTML コメントの `<!--@rv ...-->` 形式で書く。
- コメントは、対象となる見出し・段落・箇条書きの直前に置く。対象が文中の一部だけの場合は、コメント内で対象語句を明示する。
- １つのコメントには１つの論点を書く。複数の修正方針がある場合は、コメントを分ける。
- 指示には「何をどう直すか」を具体的に書く。単なる感想だけで終わらせない。
- 校正対応時は、`<!--@rv ...-->` コメントを読んで本文へ反映し、対応済みのコメントは削除する。
- `@rv` コメントは一時的な作業用とし、恒久的な執筆方針になった内容はこの `STYLE.md` に転記する。
